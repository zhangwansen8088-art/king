# 旧数据盘点与迁移边界

盘点时间：2026-10-25（北京时间）

## 1. 当前结论

- 新系统的业务规则参考了旧系统，但旧数据尚未导入 PostgreSQL。
- 当前可用的 `promotion.sqlite` 来自旧 PHP 的本地演示初始化逻辑，不是生产数据库。
- 演示库包含预设账号、演示资金和测试任务，不能作为真实商户、真实用户或真实资金的验收依据。
- 旧库没有身份证件、企业主体或第三方实名结果，不能声称数据已经过身份认证。
- 本文只完成只读盘点，不代表已经批准数据迁移。

## 4. 表映射草案

| 旧表                  | 新模型                    | 迁移要求                                                            |
| --------------------- | ------------------------- | ------------------------------------------------------------------- |
| `business_user`       | `User`、`MerchantProfile` | 整数 ID 稳定映射为 UUID；商户资料与登录账号拆分                     |
| `business_wallet`     | `Wallet`                  | 余额必须与流水累计逐账号对账                                        |
| `business_task`       | `Task`                    | 商户用户 ID 映射为 `MerchantProfile.id`；`stock` 映射为 `maxClaims` |
| `business_submission` | `Submission`              | 保留自动通过记录及原因；审核人为空不能擅自补人                      |
| `business_ledger`     | `LedgerEntry`             | 金额、前后余额、幂等键和来源单据必须原样可追溯                      |
| `business_recharge`   | 暂无同名新模型            | 不能直接丢弃，需先决定保留模型或归档映射                            |
| `business_withdrawal` | `Withdrawal`              | 旧 `cancelled` 新模型没有对应枚举，需确认业务含义                   |
| `business_audit_log`  | `AuditLog`                | 保留原操作者、动作、对象和时间                                      |

## 5. 阻断项

1. 数据来源不是生产库，必须先由业务对方确认迁移对象到底是演示数据、验收数据还是另一份生产快照。
2. 旧密码为 60 位 `$2y$` 哈希，新系统使用 Argon2id，不能原样作为已认证账号登录。应加入安全升级流程或要求重置密码，不能静默伪造密码。
3. 旧任务配置包含一级、二级、三级返佣；新 `Task` 只有 `referralCents` 一个字段，当前演示库也确实存在二、三级返佣流水。直接迁移会丢失层级语义。
4. 新系统没有与 `business_recharge` 完全对应的模型，现有充值记录无法无损映射。
5. 旧 `withdrawal.status='cancelled'` 在新枚举中不存在。本演示库暂无该状态，但通用迁移必须处理。
6. 旧库没有主体认证资料，不能把手机号、账号或管理员确认当成实名认证。

## 6. 后续门槛

真实导入前必须依次通过：

1. 业务对方按 [旧数据迁移业务确认表](data-source-confirmation.md) 书面确认唯一数据源、截止时间和资金处理方式。
2. 完成一、二、三级返佣、充值单和取消提现的模型决策。
3. 在隔离 PostgreSQL 测试库执行可重复导入。
4. 逐表核对数量、金额、时间、幂等键和内容指纹。
5. 执行一次全新环境恢复演练，并由业务对方确认验收结果。
6. 通过后再单独批准生产切换。
